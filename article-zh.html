Leaf 经典美少女游戏（LVNS）逆向与 macOS Swift 原生移植工程指南

——基于《雫～しずく～》的 Windows 95 老游戏现代重构实录

🌐 多语言版本 / Language: 🇨🇳 简体中文 ｜ 🇺🇸 English ｜ 🇯🇵 日本語

本文档是一份面向现代软件工程师的务实技术总结。内容记录了如何将 Leaf（AQUAPLUS 前身）在 1996 年发布的视觉小说《雫～しずく～》（以及同架构的 LVNS 引擎家族）从 Windows 95 的老旧数据中解构，并使用现代 Swift 与 Metal 图形管线在 macOS（Apple Silicon）上原生重写为 60Hz 独立应用（Ver.1.0）的完整工程流程。

文档剔除所有故事化与修饰性描述，专注于实打实的技术细节：二进制数据逆向、Opcode 语义推导、双层虚拟机设计、渲染与音频踩坑排查，以及将整套方法复用到《痕》和《To Heart》的具体工程工序。

1. 项目目标与总体架构决策

1.1 为什么放弃 Wine / 虚拟机方案

在将 90 年代老游戏移植到现代 macOS（Apple Silicon）平台时，常见做法是打包 Wine 环境或使用现成模拟器。但实际评估后发现该方案存在若干无法接受的工程缺陷：

  1. Retina 与显示集成差：Wine 处理 640×400 这种低分辨率 8 位/16 位调色板画面时，默认拉伸往往引入双线性模糊或锯齿失真，无法原生调用 Metal 进行整倍数像素级点阵缩放；
  2. 调试能见度极低：老旧的 Win32 API 调用、DirectDraw/GDI 接口与 DirectSound 在转译层（尤其是 Rosetta 2 + Wine）中行为不可测，一旦发生内部死锁或崩溃，LLDB 和 Instruments 无法深入定位根本原因；
  3. 平台原生能力缺失：无法直接使用 macOS 原生菜单栏、无法优雅响应系统快捷键、无法原生支持触控板手势、且存在进程退出残留或 Dock 黑盒问题。

因此技术决策确立为：100% 剥离老 EXE，对数据格式与虚拟机逻辑进行白盒重构，使用原生 Swift + Metal 重新实现游戏运行时。

2. 逆向工程方法与基准确认

2.1 前人开源资产的参考价值与局限

在解析 Leaf 的 LVNS（Leaf Visual Novel System）引擎时，历史上有三个主要参考源：

  1. XLVNS / mglvns (Go Watanabe, 1999–2000, BSD)：
  2. 价值：提供了极其详尽的 C 语言实现，涵盖了 LEAFPACK、LFG、大部分 SCN opcode 和转场逻辑。
  3. 局限：代码中充斥着 #ifdef USE_MGL 分支。这是为了适配当时低性能 Linux/X11 运行环境而做的降级实现（例如 320×200 分辨率缩减、转场步长写死为 8px）。如果直接照搬 MGL 分支，会得到与 Windows 原版完全不符的劣化行为。
  4. akkera102 的 Sizuku GBA 工具链 (个人研究用)：
  5. 价值：提供了 SCN 提取脚本原型 decscn.py 与指令定义 script.c。
  6. 局限：专为 GBA 重制版设计，部分缓冲区存在硬编码截断，字体结构与 PC 版完全异构。
  7. GBALVNS (BSD-3-Clause)：
  8. 价值：清晰的状态机模型参考。
  9. 局限：其资产全部是重新烘焙的 GBA 专用数据，不读取 Windows 原版二进制。

2.2 验证基准：EXE 静态反汇编与 Wine 动态 Oracle

当开源代码与实际现象出现分歧时，必须确立权威验证机制：

  1. Capstone + pefile 静态反汇编与字段级对齐： 原版 Sizuku.exe 是一个未启用 ASLR 且无重定位表的 32 位 PE 程序，固定加载基址为 0x400000。 通过 pefile 解析节区表（Section Table）可验证：代码段 .text（RVA 0x1000，Raw 0x1000）、常量段 .rdata（RVA 0x2E000，Raw 0x2E000）与数据段 .data（RVA 0x30000，Raw 0x30000）的内存页对齐与磁盘文件对齐完全一致（均为 0x1000 页面对齐）。因此对于全部核心代码与静态数据，内存虚拟地址（VA）与磁盘文件物理偏移严格等价： $$\text{File Offset} = \text{RVA} = \text{VA} - 0x400000$$ 在开发与排错过程中，遇到任何关于 Opcode 宽度或状态机跳转的争议，直接反汇编对应的虚拟地址机械码，即获得绝对权威的一手基准真值。
  2. Wine 作为动态 Oracle： 在 Wine 环境下运行原版游戏。遇到不确定的 opcode 或画面演出时，通过内存 dump 和断点观察原版程序在真实内存与显存中的状态，作为 Swift 实现的对照标准。

3. 基础数据格式字段级逆向与解密

3.1 LEAFPACK 归档容器（MAX_DATA.PAK）

MAX_DATA.PAK 封包包含了全部 403 个游戏文件。

+--------------------------------------------------------------------------+
| 偏移 (Offset) | 字段 (Field)    | 类型 (Type) | 说明 (Description)       |
|---------------|-----------------|-------------|--------------------------|
| 0..7          | Magic           | 8 Bytes     | 静态 ASCII 字符串 "LEAFPACK"|
| 8..9          | FileCount       | uint16_le   | 文件总数（雫原版固定为 403）|
| 10..TableEnd  | File Payloads   | Variable    | 逐字节加法滚动加密的数据区 |
| 末尾 24*N 字节| File Directory  | 24B / Entry | 目录表（同样经过滚动加密）  |
+--------------------------------------------------------------------------+

解密算法与密钥

封包数据区采用字节加法滚动混淆： $$\text{EncryptedByte} = (\text{PlainByte} + \text{Key}[k]) \pmod{256}$$ 解密即为： $$\text{PlainByte} = (\text{EncryptedByte} - \text{Key}[k] + 256) \pmod{256}$$

密钥是 11 字节序列：

static const uint8_t LEAF_KEY[11] = {
    0x71, 0x48, 0x6a, 0x55, 0x9f, 0x13, 0x58, 0xf7, 0xd1, 0x7c, 0x3e
};

目录项格式与盲破特性

目录表位于封包末尾，每个条目 24 字节： - name[8]：大写 ASCII 文件名，不足 8 字节补空格（0x20）； - ext[3]：大写扩展名（如 LFG, SCN, KNJ）； - zero：保留字节（0x00）； - offset：uint32_le，数据在封包内的绝对偏移； - length：uint32_le，解密后数据长度； - next_offset：uint32_le。

注意：解密整个封包时密钥索引 $k$ 持续递增（k = (k + 1) % 11）。由于目录表内全是已知的大写 ASCII 和空格，只要截取任意连续 3 个以上的目录项，即可通过简单的模 256 线性代数推导出完整的 11 字节密钥，无需在 EXE 里苦寻明文字符串。

3.2 LZS 压缩算法变体与输出流截断问题

Leaf 的 LZS 基于 LZSS，但工程实现中有两个极其容易踩坑的细节：

1. 正逻辑与反逻辑变体

  • 标准 lzs（正逻辑）：Flag 字节的位为 1 表示未压缩的直接字节，0 表示窗口引用。滑动窗口 0x1000 字节，初始化指针为 0xFEE。仅用于 LFG 图像数据。
  • lzs3（反逻辑）：Flag 字节取反（~flag，即 0 为直接字节，1 为引用）。滑动窗口 0x1011。SCN 脚本的事件段与消息段必须用反逻辑 lzs3 解压。

2. 输出流严格截断纪律（避免尾部数据污染）

SCN 脚本的段头明确声明了解压后的精确大小 declaredSize。 在早期实现中，若直接读取并解压直到输入流耗尽，LZSS 状态机会在遇到尾部填充对齐数据（0x00 或 0xFF）时继续解出数千字节的垃圾数据。在 197 个脚本中，有 173 个脚本尾部因此被污染，导致最后一条消息的偏移解析错乱。

解决方案：LZS 解压循环必须以 output.count < declaredSize 为硬性守卫，一旦达到声明字节数立刻终止。

3.3 LFG（LEAFCODE）图像格式与位交织

所有背景与立绘均为 .LFG 格式，文件头为 "LEAFCODE"。

+--------------------------------------------------------------------------+
| 字节范围 | 字段定义                                                      |
|----------|---------------------------------------------------------------|
| 0..7     | "LEAFCODE" 标识                                               |
| 8..31    | 16 色调色板（每色 4-bit RGB，6 字节存放 4 种颜色）             |
| 32..33   | xoffset (uint16_be)：立绘在屏幕上的 X 偏移                     |
| 34..35   | yoffset (uint16_be)：Y 偏移                                   |
| 36..37   | raw_width (uint16_be)：实际宽度 = (raw_width + 1) * 8          |
| 38..39   | raw_height (uint16_be)：实际高度 = raw_height + 1             |
| 40       | direction (uint8)：0 为列主序（Vertical）                     |
| 41       | transparent (uint8)：透明色索引（背景通常为 0xFF）            |
| 44..47   | decompressed_size (uint32_le)：解压后字节数 = w * h / 2        |
| 48..EOF  | 标准正逻辑 LZS 压缩位图流                                      |
+--------------------------------------------------------------------------+
  • 调色板颜色扩展：4-bit 分量（0..15）必须通过半字节翻倍扩展为 8-bit（0..255）： swift let r8 = (r4 << 4) | r4 let g8 = (g4 << 4) | g4 let b8 = (b4 << 4) | b4
  • 立绘尺寸与坐标：立绘解压后高度恒为 400px（与 640×400 屏幕等高），在屏幕上的渲染 $Y$ 恒为 0。三槽布局的 $X$ 坐标固定为：左槽 0、中槽 160、右槽 320。

3.4 LAC 音频容器

bgmfile.PAK 与 soundds.PAK 采用 LAC 容器格式： - 文件头 "LAC\0" + uint32_le 条目数 + 目录表（每条目 42 字节：文件名 8 字节 + 偏移 uint32_le + 长度 uint32_le）。 - bgmfile.PAK 包含 25 条 Ogg Vorbis 音频（44.1kHz / 48kHz 立体声 BGM）。 - soundds.PAK 包含 13 条 RIFF WAV 音频（单声道、11025Hz 采样率，见后文 CoreAudio 崩溃分析）。

macOS 的 AVFoundation 框架原生不支持解码 Ogg Vorbis。我们在 Swift 中直接集成 Xiph 官方的 libogg 和 libvorbis C 源码，将 Ogg 在内存中解压为 Linear PCM 后送入音频管道。

3.5 KNJ_ALL.KNJ 点阵字库的真实布局

KNJ_ALL.KNJ 文件大小恰好为 133,344 字节。由于单字为 24×24 点阵（1bpp，每字 72 字节），整个字库包含且仅包含： $$133,344 \div 72 = 1,852 \text{ 个字形}$$

物理存储格式（列平面优先）

字形数据不是常见的行主序（Row-Major），而是3 个垂直列块（Column Strip）：

+--------------------------------------------------------------------------+
|  Glyph 24x24 (72 Bytes total):                                           |
|  - Col 0 (X: 0..7)  : 24 字节 (byte 0..23)                               |
|  - Col 1 (X: 8..15) : 24 字节 (byte 24..47)                              |
|  - Col 2 (X: 16..23): 24 字节 (byte 48..71)                              |
|                                                                          |
|  每个字节代表一行的 8 个像素，最高位 (Bit 7) 代表该列块的最左侧像素。    |
+--------------------------------------------------------------------------+

Swift 采样公式：

public func pixel(atX x: Int, y: Int, inGlyph glyph: [UInt8]) -> Bool {
    guard x >= 0, x < 24, y >= 0, y < 24 else { return false }
    let col = x / 8
    let bit = 7 - (x % 8)
    let byte = glyph[col * 24 + y]
    return ((byte >> bit) & 1) != 0
}

1-based 叶码与 sizfont.tbl

  • 叶码（Leaf Code）：脚本中引用的 2 字节代码，直接对应字库槽位： $$\text{Slot Index} = \text{Leaf Code} - 1$$ 叶码为 0 时代表全角空格，只前进坐标不执行绘制。
  • sizfont.tbl（3,703 字节）：包含 1,851 个 EUC-JP 字符对。该表仅供文本导出工具使用，引擎渲染时直接用叶码访问字库，完全不查此表。

4. 双层虚拟机（VM）架构设计与逆向实现

4.1 SCN 脚本文件结构与 Block 机制

每个 SCN%03d.DAT 包含两个段： - 偏移 0..1：uint16_le，事件段在文件内的起始位置（数值 $\times 16$）； - 偏移 2..3：uint16_le，消息段在文件内的起始位置（数值 $\times 16$）。 两段分别由反逻辑 lzs3 解压。

事件段内部由 Block（块）组成。头部是一个 uint16_le 数组，记录各 Block 的起始偏移。 Block 是剧本跳转与存档还原的最小单位。

4.2 外层事件虚拟机（Event VM）与 Skip 指令陷阱

外层 VM 负责流程控制。常见 Opcode 包括： - 0x00：Block 结束； - 0x04：JUMP scn, blk（跳转至目标剧本的指定 Block）； - 0x05：SELECT（分支选择肢）； - 0x0a：设置背景地点； - 0x14：完全清屏（清空图层与文字）； - 0x22：单槽立绘加载； - 0x24：特写立绘（强制居中槽位 'c'）； - 0x38：更新画面（LvnsDisp），同时触发排队中的 BGM 开始播放； - 0x3d/0x3e：根据 flag 条件相对跳转； - 0x47/0x48：flag 赋值与累加； - 0x54：调起内层消息段对应索引的消息； - 0x6e：循环播放 BGM； - 0x7d：触发通关 Staff Roll 阻塞脚本； - 0x7e：记录通关结局编号。

Skip 占位指令

脚本中散落着 13 个占位指令（0x03, 0x06, 0x5a, 0x5c, 0x60-0x66, 0x6f, 0x73）。它们在运行时虽然不产生动作，但各自带 1~3 字节的固定长度操作数。解析时必须根据指令表吃掉对应的操作数，否则会导致后续指令流全部错位。

4.3 内层消息演出虚拟机（Inline VM）的核心地位

这是逆向 Leaf 引擎最关键的技术发现： 《雫》几乎全部的立绘、背景、CG 切换以及 BGM 和音效触发，都并非由外层事件段控制，而是作为行内控制符直接嵌入在消息文本数据流中！

当执行 0x54 调起一条消息后，解析器逐字节扫描消息段： 1. 字节 $\ge 0x80$：高位置 1，与后续字节拼接为 2 字节叶码，调用字库绘制文字； 2. 字节 $< 0x80$：控制符，驱动舞台演出： - $：消息结束，交还控制权； - p：改页等待（Page Break），点击后清空当前屏幕文字； - k/K：按键等待（Wait Key），点击后不清屏，在下行继续追加文本； - r：换行； - B/E（7 字节）：加载背景（地点编号 + 转场效果号）； - C（4 字节）：加载立绘（槽位 l/c/r + 立绘编号）； - D：清除立绘（Da 清空全部，Dl/Dc/Dr 清空特定槽）； - S（10 字节）：背景与立绘同时切换； - A/a：三人立绘排版； - V/H：全屏视觉 CG 或 H-CG； - M：BGM 控制族（Mf 淡出，Ms 暂停，Mn 排队，Mw 等待淡出完毕，M00-M25 立即切歌）； - P：PCM 音效播放（P01-P13）； - F：全屏白闪； - Q：全屏震动； - X/s：横向排版偏移与文字打印速度。

我们将每条消息解析为结构化分段：

public struct MessageSegment {
    public let actions: [InlineAction] // 该分段携带的舞台演出（立绘/背景/切歌/音效）
    public let lines: [[Int]]          // 该分段内的文字叶码
    public let pause: MessagePauseType // 待机类型：.waitKey, .pageBreak, .messageEnd
}

5. 视觉渲染管线与高保真还原工程

5.1 全屏 Sound Novel 文本网格与换行逻辑

《雫》是典型的 Sound Novel 全屏排版： - 全屏 640×400 就是文本画布； - 原点：(20, 18)； - 字符网格：25 列 × 13 行； - 字距与行距：字宽 24px（列步进 24px），行高 28px（字高 24px + 行距 4px）； - 换行规则：Windows 原版没有任何避头尾禁则。横向字符计数 cur_x > 24 时直接无条件折行。

5.2 调色板暗化与三 Pass 叠印硬阴影字绘

为了保证文字在复杂的背景图上清晰可辨，原版采用硬件调色板暗化与点阵硬阴影：

  1. 背景调色板暗化（Latitude Darkening）： 画面上有文字显示时，背景并非使用现代半透明 Alpha 遮罩，而是直接将 DAC 调色板亮度乘以衰减系数： $$\text{latitude_dark} = \frac{11}{16} = 0.6875$$ 即背景亮度整体降低 31.25%。
  2. 三 Pass 叠印字形渲染： 文字绘制直接以 1bpp 掩码对画面缓冲区进行三次印章式写入：
  3. Pass 1：向右下偏移 (x + 1, y + 1)，写入纯黑（阴影 1）；
  4. Pass 2：向右偏移 (x + 2, y + 1)，写入纯黑（加厚右侧阴影）；
  5. Pass 3：原位 (x, y)，写入纯白或浅灰（文字本体）。 掩码为 0 的像素完全透传背景，不使用任何反锯齿模糊，呈现纯粹的 1996 年点阵锐利边缘。

5.3 等待光标的精准语义与相位重置

  • 光标类型：
  • 行内按键等待（k/K）：使用字库叶码 102，绘制为向右实心箭头 ▶；
  • 改页等待（p）：使用字库叶码 103，绘制为折角纸张/文档图标。
  • 绘制位置：位于最后一行文字最后一个字之后的下一个文字网格内。
  • 点灭周期与相位问题： 光标以 6 帧亮、6 帧灭（200ms 周期）交替。 踩坑点：如果直接取全局翻转时钟 (flipCount / 6) % 2，换页停顿时可能恰好处于“灭”的半周期，导致光标在最初的 100ms 内不可见，给人以操作迟钝感。 解决方案：进入等待状态的那一刻，强制将光标基准时钟锁定为当前帧（entryFlip = flipCount），保证等待开始的第 1 帧必定处于高亮状态。

5.4 地点折叠（bgmap）与天候调色板（palmap）

剧本中出现的地点编号并不直接对应图片文件名： 1. 地点折叠（bgmap）： 56 个地点编号被折叠到 35 张 MAX_S*.LFG。例如地点 4/5 映射为 MAX_S02，地点 41/42 映射为 MAX_S15。地点 0 映射为纯黑清屏。 2. 天候调色板（palmap）： 地点 41 与 42 对应同一张教室底图，但 41 代表白天，42 代表黄昏。引擎预设了 9 档天候调色板，只动态替换底图调色板的前 4 个条目（0..3），保留第 4 个条目的常量白，实现同图不同光照。 3. VIS21 孤儿文件： 剧本中请求的 VIS21.LFG 并不存在。原版 SizukuLoadVisual 内部写死：若请求 21 号，则加载 VIS02 并强行套用紫色调色板。

5.5 13 种 CG 转场特效的数学还原与大窗适配

原版 sizuku_effect[13] 定义了 13 种经典转场（包括调色板淡变、矩形螺旋、斜切瓦片、菱形扩散、有序抖动网点、横竖梳齿等）。

  • 转场总耗时计算（以 56 帧效果为例）： 一次完整的切换 = LvnsClear（56 帧擦除旧图）+ LvnsDisp（56 帧推入新图）+ 显影后强制静止 30 帧 = 142 翻转（Flips，约 2.36 秒）。 在转场期间，解释器严格阻塞，不响应任何推进点击。
  • 大窗下的逻辑网格契约： 在 Retina 或 1280×800 窗口下，如果按实际窗口像素计算 32px 的掩码块，方块在视觉上会被缩小为原本的一半，导致画面呈现碎裂噪点感。 解决方案：将两帧图像缩小到标准的逻辑 640×400，在逻辑网格上计算转场掩码，再整数倍无损放大回实际视口。

5.6 螺旋转场（GURUGURU）算法修复

原版 1 号转场 GURUGURU 要求从中心以 16px 瓦片向外螺旋展开。 开源 mglvns 中的 #ifdef USE_MGL 分支存在严重 Bug：其循环终止条件过早触发，横向只走到了第 26 列（共 40 列），导致屏幕右侧 1/3 未被走访，落入了从上往下的行优先兜底填充。

修复：严格对齐 #ifndef USE_MGL（Windows 原版分支），在 40×25 的 16px 瓦片网格上以 (27, 12) 为中心，每半圈对称累加臂长，保证全屏 1000 块瓦片被连续的螺旋臂完全覆盖。

5.7 Opcode 0x01 过场四式与正弦背景扭曲

Opcode 0x01 是复合过场： - 第 1 式：开启正弦背景扭曲，文字打印后调色板淡到黑； - 第 2 式：淡入同时维持正弦扭曲； - 第 3 式：阻塞式题字动画（sizuku01 38 帧 / sizuku02 19 帧）； - 第 4 式：普通消息。

正弦扭曲的数学与渲染管线相位

核心依赖包含 361 个采样点的查找表 sintable[361]（1° 采样，振幅 $\pm 160\text{px}$）。因首尾填 0，整张表求和恒为 -1（历史固有特征，不可修改）。 关键渲染相位：扭曲采样必须发生在背景 Blit 之后、立绘合成与文字绘制之前。行偏移公式为 vram[x] = bg[x + shift]。立绘和文字叠加在扭曲后的背景上，因此文字笔直而背景剧烈波动。

5.8 全屏回想模式（LvnsHistory）与双重文字 VRAM

  • 进入回想时保存当前场景状态，退出时一键还原，实现主干状态零污染；
  • 背景图层保持不变，文字层切入 current_tvram = 1，一次性输出全页文字；
  • 脚本内的 14 处 if (!history_mode) 守卫自动旁路立绘、音效与等待指令；
  • 界面上的 ▲ / ▼ 不是图形按钮，而是第 25 列的文本字符格，通过读取命中格的属性响应翻页。

6. 音频系统与 macOS 底层工程排错

6.1 BGM 编号映射（bgmmap）与音轨偏移

游戏剧本内的 BGM 编号不是物理文件编号，必须经过 bgmmap 转换：

int bgmmap(int script_no) {
    if (script_no == 14) return 2;  // 特例：指向音轨 2 (Jingle)
    if (script_no < 16)  return script_no + 2;
    return script_no + 1;
}

物理文件名为 MUS(track - 2).OGG。若漏掉此映射，会导致全剧本 30% 以上的场景播放错误的音乐。 我们通过对 1996 年发售的官方原声 OST 运行声纹比对，以 0.898 的置信度锁定了 OP 曲正是 78.2 秒的 MUS14.OGG（而非 219 秒的 Happy End 曲 MUS16.OGG）。

6.2 CoreAudio 单声道 11025Hz 导致的静默闪退

在解析包含音效的消息时，曾遭遇进程假死、CPU 占满且无任何错误输出的严重故障。

根本原因

soundds.PAK 内的音效为 11025Hz 单声道 WAV。 macOS 的 AVAudioEngine 主混音节点工作在 48000Hz 立体声。 当调用 AVAudioPlayerNode.scheduleBuffer 传入声道或采样率不匹配的缓冲区时，CoreAudio 底层抛出 Objective-C NSException。 在命令行 CLI 中，该异常会导致进程崩溃并打印调用栈；但在 AppKit GUI 应用程序中，NSApplication 主 RunLoop 顶层默认包裹了 @catch，静默吞掉了这个异常并展开了调用栈，导致解释器瞬间消失，现象表现为无报错卡死。

修复

在 AudioController 中实现通用转换层：

private func convertedBuffer(from inputBuffer: AVAudioPCMBuffer, to targetFormat: AVAudioFormat) -> AVAudioPCMBuffer {
    if inputBuffer.format == targetFormat { return inputBuffer }
    guard let converter = AVAudioConverter(from: inputBuffer.format, to: targetFormat) else { return inputBuffer }
    let capacity = AVAudioFrameCount(Double(inputBuffer.frameLength) * targetFormat.sampleRate / inputBuffer.format.sampleRate) + 1024
    guard let outputBuffer = AVAudioPCMBuffer(pcmFormat: targetFormat, frameCapacity: capacity) else { return inputBuffer }
    var error: NSError?
    converter.convert(to: outputBuffer, error: &error) { _, outStatus in
        outStatus.pointee = .haveData
        return inputBuffer
    }
    return outputBuffer
}

6.3 60Hz 宇宙时钟与 macOS App Nap 节流问题

Leaf 引擎的时间基准是 1/60 秒（1 Flip），由 INTERVAL = 60 规定。

App Nap 导致的 1/12 慢动作

实机测试中出现过光标闪烁与文字打字极慢的现象。 经排查，当窗口未处于前台活动状态或系统判断负载较低时，macOS 的 App Nap 机制将定时器节流至 ~1Hz。即使定时器有补帧逻辑，整个游戏也退化为每秒 5 帧，相当于原速的 1/12。

解决手段

在 60Hz 循环生命周期内向系统显式注册电源管理延迟断言：

self.activityToken = ProcessInfo.processInfo.beginActivity(
    options: [.userInitiated, .latencyCritical],
    reason: "60 Hz reference flip loop (Lvns INTERVAL)"
)

7. 逆向攻坚实战：标题画面隐藏音乐室（音楽モード）

7.1 突破口：标题菜单第 5 个隐藏指针

历史开源实现 mglvns 中将音乐室相关逻辑注释为 #if 0，曾让外界一度误认为 Windows 原版未实现该功能。 通过 Capstone 对 Sizuku.exe 标题菜单指针数组（VA 0x430ebc，对应文件物理偏移 0x30ebc）进行反汇编与内存解析，确凿发现该数组实际容纳了 5 个菜单项指针（0x00430ebc, 0x00430ed0, 0x00430ee4, 0x00430ef8, 0x00430f0c），而非界面上可见的 4 项。 前 4 项为可见菜单文本（如“最初から”、“栞から”等）；而位于 0x00430f0c 的第 5 个指针指向一段极其特殊的叶码数据流： 73 30（"s0"，样式 0） + 58 35 36 59 31 32 38（"X56Y128"，ASCII 绝对坐标码） + ff ff（全角空格叶码） + 72 24（"r$"，换行与字符串结束符）。 这正是一个文本内容全为空格（屏幕渲染完全透明）、但通过独立坐标码单点定位在屏幕特定区域的隐形菜单命中槽！当点击该判定区时，菜单派发表 0x409558 的 Case 4 触发，直接跳转至 0x408d40 进入原版音乐室。

7.2 坐标换算与像素对齐

Leaf 坐标编码规则： - Y：以 1 像素为单位； - X：以 8 像素（半角字宽）为单位。

因此入口绝对物理坐标为： $$X = 56 \times 8 = 448\text{px}, \quad Y = 128\text{px}$$ 在 640×400 标题背景 TITLE0.LFG 上投影，该点恰好死死对齐校舍右侧大楼上排窗户最右侧的一格。

7.3 音乐室代码与字符串 0x24 截断陷阱

跟踪跳转至 0x408d40，确认为独立音乐播放器： - 底板为 VIS17.LFG（八音盒插画）； - 包含 24 首曲目名与作曲家表； - 解码陷阱：曲名以 0x24（ASCII $）结尾，但 0x24 同时也是合法日文叶码的第 2 字节（例如「叔父さん」的「叔」）。如果盲目按字节匹配 0x24 截断，会导致曲名在中间断裂。解码器必须按 2 字节对齐步进匹配。

8. 通关 Staff Roll 阻塞式长脚本解析

由 0x7d END_BGM 触发的通关演职员名单是阻塞式流程： 1. 共有 14 张画面卡片，每张按时序循环：背景就绪 $\to$ 文字静止 6 秒 $\to$ 调色板 16 步暗转 $\to$ 新底板 16 步显影 $\to$ 底板纯画面静止 1 秒 $\to$ 文字落定； 2. 全流程时长严密固定为： $$16 + (13 \times 436) + 76 = 5760 \text{ Flips} \approx 96 \text{ 秒}$$ 3. CLICK_JUMP 机制：玩家点击时不会立即跳出，而是记录 selectPending，等待当前卡片 6 秒倒计时走完当前拍的边界，再平滑切入最终版权卡。

  9. 反汇编备用：使用 Capstone 随时定位跳转表与字符串段。

10. 验证工具与调试工程基建

10.1 无头自动化导帧工具（SHIZUKU_SHOT）

为避免测试断言全绿但画面实际为空（如渲染顺序颠倒导致背景覆盖文字）的欺骗性问题，运行时内建了无头导帧工具：

SHIZUKU_SHOT=boot,title,game,esc,spiral,music ./build/ShizukuApp

工具模拟离散时钟步进，无损导出各阶段 640×400 RGBA 画布为 PNG。工程规定：所有视觉层修复必须以目检导出的 PNG 图像为准。

10.2 生产环境内置的翻转番犬（Watchdog）

Release 版本内置独立主线程看门狗： 在引擎处于活跃状态（转场、打印、快进）时，若超过 2.0 秒未收到 Flip 心跳，看门狗记录崩溃上下文（scn, blk, pc, 底板名, 转场状态）至 ~/Library/Logs/Shizuku_Restored/diagnostic.log，并强制重启底层 DisplayLink 循环执行原地自愈，保证长流程游玩不卡死。
