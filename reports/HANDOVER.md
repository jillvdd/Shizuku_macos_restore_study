## 1. 工程背景与现代重构决策

本项目旨在针对 Leaf（现 AQUAPLUS）于 1996 年发布的视觉小说开山之作《雫～しずく～》（以及同架构的 LVNS 引擎家族），脱离老旧 Windows 平台环境，在现代 macOS（Apple Silicon, Swift + Metal）上构建一套高保真、独立运行的原生 60Hz 游戏系统。

### 1.1 为什么放弃 Wine / 兼容层方案
在立项前期，团队曾搭建并测试了 Wine 11.15 及相关虚拟化容器方案。实机测试暴露出三大难以逾越的工程缺陷：
1. **音频混音时钟失步**：Windows 95 时代的 DirectSound / waveOut API 依赖硬件中断与独占缓冲区，在现代 macOS 的 CoreAudio 用户态模拟层中频繁出现音频缓冲区欠载（Underrun），导致 BGM 循环缝合处出现爆音与随机卡顿。
2. **图形缩放模糊与高刷撕裂**：640×400 原始分辨率在 Wine 窗口化下使用未经优化的双线性插值，字形与 16 色像素边缘严重模糊；且无法利用 macOS ProMotion 动态刷新率特性，画面出现微抖动（Micro-stuttering）。
3. **平台原生融合度断层**：兼容层无法提供原生的 macOS 菜单栏快捷键、高精度触控板平滑回想（Backlog）滚动、视网膜屏整数倍等比居中，以及标准 JSON 格式的持久化存档。

因此，团队决定采用 **Swift + Metal 纯原生重写路线**。

### 1.2 现代模块化分层架构
整个工程在 Swift Package Manager 规范下划分为四个高度解耦的模块：
- **`ShizukuCore`**：底层二进制 I/O、LEAFPACK 11 字节流式解密、LZS3 变体解压、KNJ 24×24 物理字模展开、LFG 图像解码。
- **`ShizukuEngine`**：外层事件虚拟机（Event VM）、内层消息演出虚拟机（Inline VM）、系统旗标状态机、JSON 存档序列化。
- **`ShizukuRender`**：Metal 图形管线、640×400 离屏纹理渲染目标、25×13 Sound Novel 文字排版网格、全局调色板暗化与 13 种屏幕转场。
- **`ShizukuApp`**：macOS AppKit 原生窗口宿主、60Hz CVDisplayLink 锁相驱动、菜单栏与键盘事件调度、全屏剧情回想与隐藏音乐室控制器。

## 2. 专有归档解密与差分盲破算法

### 2.1 LEAFPACK 11 字节加法滚动密钥
游戏主数据包 `MAX_DATA.PAK`（5,756,792 字节）包含 403 个游戏资产。文件头由 8 字节魔数 `"LEAFPACK"` 及一个 16 位小端整数（文件总数 `0x0193` = 403）构成。其数据区与末尾目录区均受到 11 字节滚动异或密钥混淆。

加密算法具有**全局累加推进**特性：密钥索引 $k$ 在跨越文件边界时不重置，从数据区起始点向后连续步进。
$$\text{StoredByte} = (\text{PlainByte} + \text{Key}[k \bmod 11]) \bmod 256$$
对应解密公式为：
$$\text{PlainByte} = (\text{StoredByte} - \text{Key}[k \bmod 11]) \bmod 256$$

### 2.2 目录区槽位差分盲破推导
在没有反汇编 Windows 原版 EXE 的情况下，通过观察目录区 24 字节记录结构：
- 前 8 字节为文件名（不足 8 字节右侧以 ASCII 空格 `0x20` 填充）。
- 接下来 3 字节为扩展名（如 `"LFG"`, `"DAT"`, `"P16"`）。
- 第 11 字节固定为 `0x00`。

由于每个槽位末尾大量存在已知的连续空格字符（`0x20`），利用模 11 的线性同余相位差，仅凭目录区密文统计即可瞬间盲破出完整的 11 字节密钥：
`71 48 6a 55 9f 13 58 f7 d1 7c 3e`（ASCII 对应 `"qHjU…"`，与原版 `Sizuku.exe` 内嵌的常量字符串 `"LEAFPACKqHjU"` 完全一致）。403 个文件由此实现 100% 自动化精准无损抽取。

## 3. LZS 解压变体与 173/197 文本截断难题

### 3.1 两种 LZS 变体的物理区分
逆向确认原版数据中存在两种互不兼容的 LZS 字典压缩变体：
1. **正逻辑 LZS（用于 LFG 图像）**：标志位为正逻辑（1 代表未压缩单字节，0 代表字典滑动引用），滑动窗口大小为 `0x1000`（4,096 字节），初始填充位置为 `0x0FEE`。
2. **反逻辑 LZS3（用于 SCN 剧情脚本）**：标志位取反（`~flag`，0 代表未压缩字节，1 代表字典引用），滑动窗口大小为 `0x1011`（4,113 字节）。

### 3.2 173/197 脚本末尾垃圾字节截断攻坚
在早期阶段，使用历史开源工具解压 SCN 消息段时，发现 197 个脚本中有 173 个脚本末尾会出现不同程度的乱码崩溃。
深入排查发现：原版打包工具在写入 LZS 压缩流时，字典压缩器在最后一个压缩块后写入了不定长的填充垃圾字节。解压算法**必须严格依据 SCN 块头声明的解压后字节数进行硬截断**。一旦解压字节数达到段头声明大小，必须立即中止滑动窗口循环并封闭输出流。实施该截断策略后，全量 197 个脚本末尾乱码彻底归零。

## 4. KNJ 点阵字库物理排布与寻址推导

`KNJ_ALL.KNJ`（133,344 字节）是《雫》的专属点阵字库文件。
- **字形总数**：$133,344 \div 72 = 1,852$ 个字形。
- **字模规格**：每个字模为 24×24 像素、单色 1bpp，占用 72 字节。
- **内存排列**：采用 3 列垂直扫描带（Vertical Strip）排布，每列 24 像素占用 24 个连续字节，MSB 位于列顶端。

### 纠正历史认知误区：1-based 直接数组寻址
过去部分逆向资料误认为 Leaf 文字编码与 Shift-JIS 存在复杂的算法哈希映射，甚至猜测需依赖庞大的动态转换表。
实机验证最终确认：原版 SCN 消息流中高位被置位的双字节数值（Leaf 字形码）是**直接的 1-based 数组物理索引**：
$$\text{GlyphOffset} = (\text{leaf\_code} - 1) \times 72$$
`sizfont.tbl` 仅为外部研究者反向对照 Shift-JIS 的参考字典，引擎内部直接拿叶码取模寻址即可输出正确字形。

## 5. 双层嵌套虚拟机设计与 Opcode 调度

游戏运行时呈现典型的**双层嵌套虚拟机架构**：

```text
       [ SCN 文件二进制 ]
               │
       ┌───────┴───────┐
       ▼               ▼
 ┌───────────┐   ┌───────────┐
 │ 事件段    │   │ 消息段    │
 └─────┬─────┘   └─────┬─────┘
       ▼               ▼
 ┌───────────┐   ┌───────────┐
 │ Event VM  │──▶│ Inline VM │
 └───────────┘   └───────────┘
 (场景流/跳转)     (逐字演播/内联宏)
```

### 5.1 外层事件虚拟机（Event VM）
负责剧本的大粒度跳转、分支选择（`0x05`）、立绘与背景槽位挂载、系统旗标运算（`0x3d`-`0x48`）以及通关结局判定（`0x7e`）。
在事件流中，团队精准排查并识别出 **13 个带操作数却无实际动作的 Skip Opcode**（如 `0x03`, `0x06`, `0x5a`, `0x5c`, `0x60-0x66`, `0x6f`, `0x73`）。虚拟机必须精确测量各指令的操作数宽度并在解释器中安全步进，否则会导致程序计数器（PC）错位，引发不可逆的逻辑死锁。

### 5.2 内层消息演出虚拟机（Inline VM）
原版《雫》90% 的舞台演出并不发生在外层事件流中，而是以 ASCII 内联宏字符直接嵌入对话文本流：
- `B/E`：背景平滑置换（含转场特效号）
- `C` / `D`：立绘加载与特定槽位消隐
- `S`：背景与立绘原子级同步切换
- `A`：三立绘同屏排布
- `M` / `P`：BGM 切换、渐隐与 PCM 音效触发
- `F` / `Q`：白屏闪烁与画面暗化震屏

## 6. 视觉管线还原与 13 种转场几何数学

### 6.1 Sound Novel 文本网格与三 Pass 阴影字
- 画布基准分辨率：640×400。
- 文本排版网格：严格遵循 $25 \times 13$ Sound Novel 文字矩阵，字宽 24px，字距 1px，行距 6px，屏幕左/上边缘预留 20px 安全边距。
- 三 Pass 阴影字绘制：原版文字带有鲜明的黑色硬阴影。现代 Metal 渲染器通过在 $(X+1, Y+1)$ 位置优先渲染硬黑底层，再在 $(X, Y)$ 叠加原字形，完美还原 Windows 95 原版扎实质感。

### 6.2 螺旋转场（GURUGURU）几何还原
原版引擎中最具代表性的转场是螺旋转场（GURUGURU）。通过反汇编还原其离散网格数学：
- 屏幕划分为 $40 \times 25$ 个 $16 \times 16\text{px}$ 瓷砖网格。
- 螺旋中心点并非数学正中心，而是位于坐标 $(X=27, Y=12)$。
- 算法由中心出发，按「右 $\to$ 下 $\to$ 左 $\to$ 上」步进向外旋进，并在超出边界时自动环绕裁剪，实现了与原版无差别的 40 步向外螺旋渐现效果。

## 7. 原版 EXE 虚拟地址反汇编与隐藏音乐室

### 7.1 PE 内存映射与静态反汇编
在 `Sizuku.exe` 中，`.text`、`.rdata` 和 `.data` 区段均按 `0x1000` 字节对齐：
$$\text{File Offset} = \text{RVA} = \text{Virtual Address} - 0x400000$$

### 7.2 钟楼不可视点击窗格定位
原版标题画面存在一个极难发现的隐藏音乐室彩蛋。通过反汇编虚拟地址 `0x430ebc` 处的指针表，发现其包含了 5 个菜单项指针：
- 菜单 0：`"s0X23Y272͂߂r$"`（最初から）
- 菜单 1：`"s0X23Y296Âr$"`（続きから）
- 菜单 2：`"s0X23Y320󋵕\r$"`（状況表示）
- 菜单 3：`"s0X23Y344Ir$"`（終了）
- **菜单 4（隐藏项）**：位于 `0x430f0c`，内容为 `"s0X56Y128\xff\xffr$"`。

其中 `0xffff` 在 Shift-JIS 中对应全角空格，导致该点击区域在视觉上绝对隐形。根据坐标换算：
$$X = 56 \times 8 = 448\text{px}, \quad Y = 128\text{px}$$
该坐标精准落在标题画面背景图 `TITLE0.LFG` 的校舍钟楼右上角窗格位置。点击后触发 `0x409558` 分支 4，跳转至 `0x408d40` 进入专属音乐室，背景切换至 `VIS17.LFG`。现代移植版在保留彩蛋点击机制的同时，通过菜单栏与鼠标悬停白框提示大幅提升了现代可用性。

## 8. macOS 底层系统工程排错实录

### 8.1 11,025Hz 单声道 CoreAudio 崩溃被静默吞噬
**故障现象**：游戏在推进至 `SCN051` 触发某处音效时，主解释器线程突然静默中断，窗口保留画面但无法继续响应输入。
**排查复盘**：原版音效资产 `P01-P13.WAV` 为极其古老的单声道 11,025Hz 采样格式。当此类音频数据直接填充入现代 macOS 立体声 44,100Hz 的 `AVAudioPlayerNode` 时，底层 CoreAudio 节点抛出了内部格式不匹配的 `NSException`。该异常穿透回 AppKit 主事件循环后被 Cocoa 框架**静默吞没**，导致上层虚拟机调用栈被硬性中断。
**解决方案**：引入 `AVAudioConverter` 实时音频重采样管线，在音效加载时即时将其转码为 44,100Hz 立体声标准浮点音频缓冲，彻底消除了所有音频崩溃隐患。

### 8.2 macOS App Nap 对 60Hz 刷新率的极度锁频
**故障现象**：在全屏或长对话无鼠标操作状态下，画面文字打印速度突然下降至原版的 $1/10$，动画与转场发生肉眼可见的严重掉帧。
**排查复盘**：macOS 引入的 App Nap 节能机制在检测到用户较长时间未产生输入事件时，会将当前应用的能耗档位降至极低，并将高精度定时器与 DisplayLink 降频至 5 FPS。
**解决方案**：在应用生命周期管理中注入系统活动锁：
```swift
ProcessInfo.processInfo.beginActivity(
    options: [.userInitiated, .latencyCritical],
    reason: "Lock 60Hz display link for retro visual novel rendering"
)
```
成功将渲染管线死死锁定在 60.0 FPS，消除了所有运行期异常减速。

## 9. 结论与工程成果
