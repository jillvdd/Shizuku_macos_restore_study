## 1. 開発背景および設計方針の決定

本プロジェクトは、Leaf（現アクアプラス）が 1996 年に発売したビジュアルノベルの金字塔『雫～しずく～』および同系統の LVNS エンジンを対象に、旧来の Windows 実行環境から完全に脱却し、最新の macOS（Apple Silicon, Swift + Metal）上で自律動作する高忠実度なネイティブ 60Hz 実行環境を再構築することを目的としました。

### 1.1 エミュレータ／Wine 方式を排除した理由
初期プロトタイプ検証において、Wine 11.15 による実行環境を評価した結果、以下の致命的欠陥が確認されました：
1. **音声混音におけるジッターと同期破綻**：Windows 95 時代の DirectSound API は排他的ハードウェアバッファに依存しており、CoreAudio 互換層においてバッファアンダーランが頻発し、BGM ループ境界で音割れやプチノイズが発生。
2. **描画ぼやけとリフレッシュレート不一致**：640×400 の原版画面を Wine でウィンドウ表示すると不適切なバイリニア補間が適用され、16色ドット絵の鮮鋭度が喪失。さらに macOS ProMotion の可変リフレッシュレートと位相同期できず、微小なコマ落ち（Micro-stuttering）が発生。
3. **OS ネイティブ体験の欠如**：標準メニューバーのショートカット、トラックパッドによる滑らかなバックログ操作、Retina 整数倍スケーリング、JSON 形式セーブデータ等を提供できない。

これらを踏まえ、**クリーンルームによる Swift + Metal 完全ネイティブ再実装**を決定しました。

### 1.2 疎結合な分層アーキテクチャ
Swift Package Manager の仕様に基づき、システムを 4 つの独立モジュールに分割：
- **`ShizukuCore`**：バイナリ I/O、LEAFPACK 11 バイトローリング復号、LZS3 伸張、KNJ 24×24 ドットフォント展開、LFG 画像デコーダ。
- **`ShizukuEngine`**：外層イベント VM（Event VM）、内層メッセージ演出 VM（Inline VM）、システムフラグ制御、JSON セーブデータ直列化。
- **`ShizukuRender`**：Metal 描画パイプライン、640×400 オフスクリーンターゲット、25×13 サウンドノベル等幅組版、パレット暗転および 13 種トランジション。
- **`ShizukuApp`**：AppKit ネイティブウィンドウ、60Hz CVDisplayLink 位相同期、メニューバー制御、全画面バックログ、隠し音楽室コントローラ。

## 2. 独自アーカイブの暗号解読と差分盲破アルゴリズム

### 2.1 LEAFPACK 11 バイト加算循環鍵
ゲーム主アーカイブ `MAX_DATA.PAK`（5,756,792 バイト）は 403 本のアセットを内包。先頭 8 バイトのマジック `"LEAFPACK"` と 16-bit リトルエンディアンのファイル数（`0x0193` = 403）に続き、データ領域と末尾ディレクトリ領域が 11 バイトの暗号鍵で難読化されています。

暗号化は**ファイル境界を越えて連続加算される累積特性**を持ちます：
$$\text{StoredByte} = (\text{PlainByte} + \text{Key}[k \bmod 11]) \bmod 256$$
復号式は減算となります：
$$\text{PlainByte} = (\text{StoredByte} - \text{Key}[k \bmod 11]) \bmod 256$$

### 2.2 ディレクトリ差分解析による鍵の完全復元
原版 EXE を逆アセンブルすることなく、ディレクトリ領域の 24 バイト項目構造に着目：
- 0〜7 バイト：ファイル名（8文字未満は ASCII 空白 `0x20` で埋められる）。
- 8〜10 バイト：拡張子（`"LFG"`, `"DAT"`, `"P16"` 等）。
- 11 バイト目：固定値 `0x00`。

末尾に存在する連続した空白文字（`0x20`）の統計的偏りを利用し、mod 11 の位相差解析により、暗号鍵 `71 48 6a 55 9f 13 58 f7 d1 7c 3e`（ASCII `"qHjU…"`、`Sizuku.exe` 内の `"LEAFPACKqHjU"` と完全一致）を即座に特定。全 403 ファイルの完全自動抽出に成功しました。

## 3. LZS 伸張バリアントと 173/197 境界切断問題

### 3.1 2 種類の LZS バリアントの識別
解析の結果、原版リソースには互換性のない 2 系統の LZS 辞書圧縮が存在することを解明：
1. **正論理 LZS（LFG 画像）**：フラグ 1 が非圧縮バイト、0 が辞書参照。リングバッファ `0x1000`（4,096 バイト）、初期位置 `0x0FEE`。
2. **反転フラグ LZS3（SCN スクリプト）**：フラグ論理が反転（`~flag`）。リングバッファ `0x1011`（4,113 バイト）。

### 3.2 173/197 スクリプト末尾ゴミ詰まりの解消
過去のオープンソースツールで SCN を展開した際、197 本中 173 本でスクリプト末尾に文字化けが発生する問題が存在しました。
原因調査の結果、原版の圧縮器が最終マッチの後に不定長のゴミバイトをパディングとして書き出していたことが判明。展開ルーチンにおいて**ブロックヘッダに記載された展開後サイズによる厳密な強制終端切断**を実装することで、全 197 本のスクリプト末尾文字化けを完全根絶しました。

## 4. KNJ ビットマップフォント配置と配列参照

`KNJ_ALL.KNJ`（133,344 バイト）は『雫』専用の点陣字庫：
- **総文字数**：$133,344 \div 72 = 1,852$ 文字。
- **字形サイズ**：24×24 ピクセル、1bpp モノクロ、1文字あたり 72 バイト。
- **メモリ構造**：3 本の垂直走査ストリップ配置。24 ピクセル列ごとに連続 24 バイトで保持（MSB が列上端）。

### 誤解の解消：1-based 直接配列インデックス
従来の文献では Leaf 文字コードと Shift-JIS の間に複雑なハッシュ変換が存在すると推測されていましたが、実際には SCN メッセージ内の最上位ビットがセットされた 2 バイト値は、**直接の 1-based 配列物理インデックス**です：
$$\text{GlyphOffset} = (\text{leaf\_code} - 1) \times 72$$
`sizfont.tbl` は外部研究用の対照表に過ぎず、エンジン内部では葉コードから直接字形をオフセット参照して描画します。

## 5. 二層入れ子仮想マシン構造とオペコード体系

実行時システムは洗練された**二層仮想マシンアーキテクチャ**で駆動：

```text
      [ バイナリ SCN スクリプト ]
               │
       ┌───────┴───────┐
       ▼               ▼
 ┌───────────┐   ┌───────────┐
 │ イベント部│   │メッセージ部│
 └─────┬─────┘   └─────┬─────┘
       ▼               ▼
 ┌───────────┐   ┌───────────┐
 │ Event VM  │──▶│ Inline VM │
 └───────────┘   └───────────┘
 (シナリオ進行)    (文字送り/演出)
```

### 5.1 外層イベント仮想マシン（Event VM）
大粒度なブロック遷移、選択肢分岐（`0x05`）、立ち絵・背景スロット管理、システムフラグ演算（`0x3d`〜`0x48`）、およびエンディング判定（`0x7e`）を制御。
外層ストリームに存在する **13 個のダミー Skip オペコード**（`0x03`, `0x06`, `0x5a`, `0x5c`, `0x60-0x66`, `0x6f`, `0x73`）を同定し、引数長を測定して安全にステップ実行することで、プログラムカウンタのズレによる進行停止を回避。

### 5.2 内層メッセージ演出仮想マシン（Inline VM）
原版『雫』の演出の 90% は会話テキスト内に埋め込まれた ASCII インラインマクロで実行：
- `B/E`：背景転換（エフェクト番号指定）
- `C` / `D`：立ち絵ロードおよびスロット消去
- `S`：背景・立ち絵の原子的一括転換
- `A`：3人立ち絵同時配置
- `M` / `P`：BGM フェード／切替、PCM 効果音トリガー
- `F` / `Q`：画面白フラッシュ、パレット暗転・画面揺れ

## 6. 描画パイプラインとトランジション幾何計算

### 6.1 サウンドノベル組版と影文字描画
- 基準解像度：640×400。
- 組版グリッド：25 列 × 13 行の等幅配置、字間 1px、行間 6px、画面端セーフマージン 20px。
- 3 パス硬影文字重ね描き：$(X+1, Y+1)$ に黒の影ドットを描画した上で $(X, Y)$ に本文ドットを合成し、Windows 95 原版の重厚な視覚体験を再現。

### 6.2 螺回転換（GURUGURU）幾何アルゴリズムの復元
原版を象徴する螺回転換エフェクトを離散幾何学に基づき再構築：
- 画面を $40 \times 25$ 個の $16 \times 16\text{px}$ タイルグリッドに分割。
- 螺旋中心は画面中央ではなく $(X=27, Y=12)$ に位置。
- 「右 $\to$ 下 $\to$ 左 $\to$ 上」のベクトルで外向きに旋進し、40 ステップの螺旋ワイプを完全に再現。

## 7. EXE 逆アセンブルと時計塔の隠し音楽室

### 7.1 PE 仮想アドレス解析
`Sizuku.exe` において、各セクションは `0x1000` 境界に配置：
$$\text{File Offset} = \text{RVA} = \text{Virtual Address} - 0x400000$$

### 7.2 隠し判定領域の座標算出
タイトル画面のポインタテーブル VA `0x430ebc` を逆アセンブルし、5 つのメニュー項目を特定：
- 項目 0〜3：最初から／続きから／状況表示／終了
- **項目 4（隠し要素）**：`0x430f0c` の `"s0X56Y128\xff\xffr$"`。

Shift-JIS において `0xffff` は全角空白であり、判定領域が完全に見えなくなっています。座標を換算：
$$X = 56 \times 8 = 448\text{px}, \quad Y = 128\text{px}$$
この座標は背景 `TITLE0.LFG` の時計塔右上窓に一致。クリックにより `0x409558` の case 4 を経由して `0x408d40` の音楽室へジャンプし、`VIS17.LFG` 上で音楽室が起動します。

## 8. macOS 低レイヤー障害追究とシステム堅牢化

### 8.1 11,025Hz モノラル音源によるサイレントクラッシュの解明
**現象**：`SCN051` の効果音再生時にスレッドが突然中断し、応答不能となる。
**原因**：原版効果音 `P01-P13.WAV` は 11,025Hz モノラル音源であり、これをステレオ 44,100Hz の `AVAudioPlayerNode` に直接渡すと CoreAudio 内部でフォーマット不一致の `NSException` が発生。この例外が AppKit イベントループ内で**サイレントに破棄**され、VM コールスタックが断絶していた。
**解決策**：`AVAudioConverter` を組み込み、ロード時に 44,100Hz ステレオ Float32 へ動的リサンプリングを実施して根治。

### 8.2 macOS App Nap による 60Hz クロックダウンの抑止
**現象**：全画面表示や文字入力待機中に、文字送り速度が 1/10 に落ち、アニメーションが 5 FPS まで急減。
**原因**：macOS App Nap がユーザー入力の途絶を検知し、タイマー頻度を強制的に引き下げていた。
**解決策**：システム活動アサーションを注入：
```swift
ProcessInfo.processInfo.beginActivity(
    options: [.userInitiated, .latencyCritical],
    reason: "Lock 60Hz display link for retro visual novel rendering"
)
```
いかなる状態でも 60.0 FPS を死守する堅牢性を確立しました。
