## 1. 技術的目標とアーキテクチャの選定方針

### 1.1 Wine / 仮想マシン方式を破棄した理由

90年代のレトロゲームを現代のmacOS（Apple Silicon）環境へ移植する際、Wineプレフィックスの同梱やエミュレーションラッパーの採用が真っ先に検討されがちである。しかし、初期検証の段階で以下の決定的な技術的欠陥が判明し、この方針は破棄された：

1. **Retinaディスプレイと拡大スケーリングの破綻**：Wineは640×400の低解像度パレットバッファを単純なバイリニア補間で引き伸ばすため、文字ドットのエッジが不鮮明になり、Metalを用いた正確な整数倍ニアレストネイバー拡大ができない。
2. **デバッグの不透明性**：古いWin32 GDI、DirectDraw、DirectSoundコールがRosetta 2とWineを経由する構成では、予期せぬ競合やハングが発生した際に、LLDBやInstrumentsを用いてバイト単位のスタックトレースやプロファイリングを行うことが極めて困難である。
3. **ネイティブUI連携の欠如**：macOS標準メニューバーの統合、システムショートカットの連携、トラックパッドジェスチャーのサポート、Dockアイコンのスマートな挙動制御が一切行えない。

これにより、**レガシーPE実行ファイルを完全に破棄し、データ構造と仮想マシン仕様をゼロからホワイトボックス化して、SwiftとMetalで100%ネイティブ再構築する**という設計方針が確定した。

### 1.2 Swift + Metal による現代的レイヤード設計

実装はSPM（Swift Package Manager）を用い、`ShizukuRuntime`配下に4つのモジュールを明確な単方向依存関係で構築した：

## 2. リバースエンジニアリング手法と検証基準

### 2.1 先行オープンソース資産の価値と落とし穴

LVNSエンジンを解析する上で、過去の先人による3つのコードベースが参照可能であった：

1. **XLVNS / mglvns (Go Watanabe, 1999–2000, BSD)**：
   - *価値*：C言語による網羅的な実装。LEAFPACK、LFG、多くのSCN opcode、トランジションが網羅されている。
   - *注意点*：コード内に大量の`#ifdef USE_MGL`ブランチが存在する。これは1999年当時の低スペックなLinux/X11（320×200解像度）向けの回避コードであり、**これを無批判に移植するとWindowsオリジナル版と異なる壊れた挙動を引き起こす**。
2. **akkera102 GBA ツールチェーン (個人研究用)**：
   - *価値*：SCN抽出スクリプト`decscn.py`および命令定義`script.c`を提供。
   - *注意点*：GBAハードウェア特化のため固定長バッファ切り詰めがあり、フォント構造がPC版と非同型。
3. **GBALVNS (BSD-3-Clause)**：
   - *価値*：状態遷移の設計参考。
   - *注意点*：独自に再変換されたGBA用アセットのみを読み、Windows版元データを直接扱わない。

### 2.2 正解基準の確立：静的逆アセンブルと Wine 動的 Oracle

仕様の齟齬を排除するため、以下の2つの絶対的検証基準を運用した：

1. **Capstone + pefile による静的逆アセンブル**：
   オリジナル版の`Sizuku.exe`は、ASLR無効かつ再配置情報のない32ビットPE形式であり、ロードアドレスは`0x400000`で固定されている。
   ファイルオフセットと仮想アドレス（VA）の関係は常に固定である：
   $$\text{File Offset} = \text{VA} - 0x400000$$
   疑義が生じた箇所は、EXEの該当する機械語命令やジャンプテーブルを直接逆アセンブルして裁定した。
2. **Wine を用いた動的 Oracle**：
   画面描画や演出タイミングの挙動に疑問が生じた場合、Wine 11.15上でオリジナル版を実行し、ブレークポイントとメモリダンプによって実機VRAMの各フレームの状態を客観的「正解（Ground Truth）」として採取した。

## 3. バイナリデータ形式のフィールド単位解析と復号仕様

### 3.1 LEAFPACK アーカイブコンテナ（MAX_DATA.PAK）

全403ファイルが`MAX_DATA.PAK`に格納されている。

```
+--------------------------------------------------------------------------+
| オフセット    | フィールド名    | 型          | 説明                     |
|---------------|-----------------|-------------|--------------------------|
| 0..7          | Magic           | 8 Bytes     | 固定文字列 "LEAFPACK"    |
| 8..9          | FileCount       | uint16_le   | 格納ファイル数（雫は 403）|
| 10..TableEnd  | File Payloads   | 可変長      | 巡回加算暗号化データ領域 |
| 末尾 24*N B   | File Directory  | 24B / Entry | 暗号化ディレクトリ構造体 |
+--------------------------------------------------------------------------+
```

#### 暗号化アルゴリズムと復号

データ領域は**バイト巡回加算暗号**で難読化されている：
$$\text{EncryptedByte} = (\text{PlainByte} + \text{Key}[k]) \pmod{256}$$
復号は単なる減算である：
$$\text{PlainByte} = (\text{EncryptedByte} - \text{Key}[k] + 256) \pmod{256}$$

鍵は11バイトの静的配列である：
```c
static const uint8_t LEAF_KEY[11] = {
    0x71, 0x48, 0x6a, 0x55, 0x9f, 0x13, 0x58, 0xf7, 0xd1, 0x7c, 0x3e
};
```

#### ディレクトリ構造と自動鍵推測
ファイル末尾のディレクトリテーブル（各エントリ24バイト）：
- `name[8]`：大文字ASCIIファイル名、余白はスペース（`0x20`）；
- `ext[3]`：大文字拡張子（`LFG`, `SCN`, `KNJ`）；
- `zero`：パディング（`0x00`）；
- `offset`：uint32_le、コンテナ内の絶対開始オフセット；
- `length`：uint32_le、展開後のデータサイズ；
- `next_offset`：uint32_le。

*注釈*：キーインデックスはファイル間を跨いで連続的に進む（`k = (k + 1) % 11`）。ディレクトリエントリは大文字ASCIIとスペースで占められているため、任意の連続する3エントリ以上を切り出せば、EXEを読まずとも連立一次合同方程式によって11バイトの鍵配列を100%自動推測可能である。

### 3.2 LZS 圧縮の変種と出力ストリーム切り詰めの鉄則

LeafのLZSS変種（LZS）の実装には、2つの重大な落とし穴が存在する：

#### 1. 正論理と反転論理の使い分け
- **標準 `lzs`（正論理）**：フラグビットが1で直接データ、0で辞書参照。リングバッファ`0x1000`バイト、初期ポインタ`0xFEE`。**LFG画像ビットマップ専用**。
- **`lzs3`（反転論理）**：フラグビットが反転（`~flag`、0で直接、1で参照）。リングバッファ`0x1011`バイト。**SCNスクリプトのイベント部およびメッセージ部に適用**。

#### 2. 出力ストリームの厳格な切り詰め（末尾ゴミデータの遮断）
SCNスクリプトのヘッダには、展開後の正確なサイズ`declaredSize`が記述されている。
入力ストリームが尽きるまで無制限に解凍を続けると、LZSSアルゴリズムは末尾のアライメントパディング（`0x00`や`0xFF`）を誤ってデコードし続け、巨大なゴミデータを生み出す。197個のスクリプトのうち、**173個のスクリプト**でこの末尾汚染が発生し、最終メッセージのオフセットが破壊されていた。

**対策**：解凍ループは`output.count == declaredSize`に達した瞬間、強制的にブレークさせなければならない。

### 3.3 LFG（LEAFCODE）画像フォーマットとビットインターリーブ

静止画アセットはすべて`.LFG`形式であり、先頭マジックは`"LEAFCODE"`である。

```
+--------------------------------------------------------------------------+
| バイト範囲 | フィールド定義                                              |
|------------|-------------------------------------------------------------|
| 0..7       | 固定マジック "LEAFCODE"                                     |
| 8..31      | 16色パレット（4-bit RGB、6バイトで4色をパッキング）          |
| 32..33     | xoffset (uint16_be)：立ち絵の画面配置Xオフセット            |
| 34..35     | yoffset (uint16_be)：画面配置Yオフセット                    |
| 36..37     | raw_width (uint16_be)：実横幅 = (raw_width + 1) * 8         |
| 38..39     | raw_height (uint16_be)：実縦幅 = raw_height + 1             |
| 40         | direction (uint8)：0 は列主序（Vertical）                   |
| 41         | transparent (uint8)：透明色インデックス（背景は 0xFF）       |
| 44..47     | decompressed_size (uint32_le)：解凍後サイズ = w * h / 2     |
| 48..EOF    | 標準正論理 LZS 圧縮ビットマップデータ                       |
+--------------------------------------------------------------------------+
```

- **パレット展開**：4-bitカラー成分（0..15）は、ニブル倍加によって8-bit（0..255）へ展開する：
  ```swift
  let r8 = (r4 << 4) | r4
  let g8 = (g4 << 4) | g4
  let b8 = (b4 << 4) | b4
  ```
- **立ち絵の寸法と配置**：立ち絵は解凍後の高さが常に400px（画面高さと一致）であり、描画Y座標は常に0である。3つのスロットの描画X座標は、左`0`、中央`160`、右`320`で固定されている。

### 3.4 LAC オーディオコンテナ

`bgmfile.PAK`および`soundds.PAK`はLACコンテナ形式を採用している：
- 先頭`"LAC\0"` + uint32_leエントリ数 + ディレクトリテーブル（エントリあたり42バイト：名前8バイト + オフセットuint32_le + 長さuint32_le）。
- `bgmfile.PAK`：25曲のOgg Vorbis（44.1kHz / 48kHzステレオBGM）。
- `soundds.PAK`：13音のRIFF WAV（**モノラル、11025Hz**）。

macOSのAVFoundationはOgg Vorbisコンテナのデコードに非対応であるため、Xiph公式の`libogg`および`libvorbis`を静的リンクし、メモリ上で32-bit Float PCMへ直接デコードして再生する。

### 3.5 KNJ_ALL.KNJ ビットマップフォントの物理レイアウト

`KNJ_ALL.KNJ`のファイルサイズは厳密に133,344バイトである。24×24ドット文字（1bpp、1字あたり72バイト）換算で、収録文字数は：
$$133,344 \div 72 = 1,852 \text{ 文字}$$

#### 物理メモリ構造（3列縦ストリップ優先）
文字データは行主序ではなく、**3本の縦列ブロック（Column Strip）**として格納されている：

```
+--------------------------------------------------------------------------+
|  Glyph 24x24 (合計 72 バイト):                                            |
|  - 列 0 (X: 0..7)  : 24 バイト (byte 0..23)                              |
|  - 列 1 (X: 8..15) : 24 バイト (byte 24..47)                             |
|  - 列 2 (X: 16..23): 24 バイト (byte 48..71)                             |
|                                                                          |
|  各バイトは横8ピクセルを表し、最上位ビット（Bit 7）が左端ピクセルに対応する。|
+--------------------------------------------------------------------------+
```

Swift によるピクセルサンプリング処理：
```swift
public func pixel(atX x: Int, y: Int, inGlyph glyph: [UInt8]) -> Bool {
    guard x >= 0, x < 24, y >= 0, y < 24 else { return false }
    let col = x / 8
    let bit = 7 - (x % 8)
    let byte = glyph[col * 24 + y]
    return ((byte >> bit) & 1) != 0
}
```

#### 1-based 葉コードと sizfont.tbl
- **葉コード（Leaf Code）**：スクリプトに記述された2バイトの値。フォントスロットへ直結する：
  $$\text{Slot Index} = \text{Leaf Code} - 1$$
  葉コードが0の場合は全角スペースを表し、描画をスキップして座標のみ進める。
- **`sizfont.tbl`**（3,703バイト）：1,851個の葉コードをEUC-JP文字へ変換する対応表。**外部ツールによる文字列抽出用であり、ゲームの描画エンジンはこのテーブルを一切参照しない**。

## 4. 2層仮想マシン（VM）のアーキテクチャ設計と実装

### 4.1 SCN スクリプト構造と Block モデル

各`SCN%03d.DAT`は2つのセクションに分かれている：
- オフセット 0..1：uint16_le、イベント部の開始位置（値 $\times 16$）；
- オフセット 2..3：uint16_le、メッセージ部の開始位置（値 $\times 16$）。
いずれも反転論理`lzs3`で解凍される。

イベント部は先頭に各Blockのオフセット配列を持つ。
**Blockはスクリプトジャンプとセーブデータ管理の最小単位である。**

### 4.2 外側イベント仮想マシン（Event VM）と Skip 命令の罠

外側VMは進行制御を担う。主なOpcode：
- `0x00`：Block終了；
- `0x04`：`JUMP scn, blk`（指定Blockへジャンプ）；
- `0x05`：`SELECT`（選択肢分岐）；
- `0x0a`：背景地点の設定；
- `0x14`：完全画面消去（画像・テキストの両方）；
- `0x22`：単一立ち絵の表示；
- `0x24`：アップ立ち絵（中央スロット`'c'`に強制表示）；
- `0x38`：画面表示更新（`LvnsDisp`）＋ **予約BGMの再生開始トリガー**；
- `0x3d`/`0x3e`：フラグ条件相対ジャンプ；
- `0x47`/`0x48`：フラグ代入および加算；
- `0x54`：メッセージ部の指定メッセージを表示；
- `0x6e`：BGMループ再生；
- `0x7d`：スタッフロール実行；
- `0x7e`：エンディング番号記録。

#### Skip 命令のパース処理
スクリプト内には13個の何もしない命令（`0x03`, `0x06`, `0x5a`, `0x5c`, `0x60-0x66`, `0x6f`, `0x73`）が存在する。実行動作はないが1〜3バイトの固定オペランド長を持つため、パーサーはこれらを適切に読み飛ばさなければ後続の解析が破綻する。

### 4.3 内側インライン演出仮想マシン（Inline VM）の決定的一大発見

本リバースエンジニアリングにおける最大の成果：
**『雫』の立ち絵、背景、CG切り替え、BGMや効果音の発火は、外側イベント部ではなく、テキストメッセージ内のインラインASCII制御文字によってリアルタイムに駆動されている！**

`0x54`でメッセージが呼ばれると、パーサーはバイト列を走査する：
1. **バイト $\ge 0x80$**：後続バイトと結合して16ビット葉コードを生成し、フォントを描画。
2. **バイト $< 0x80$**：演出コマンドとして処理：
   - `$`：メッセージ終了；
   - `p`：改ページ待機（Page Break）。入力待ち後、画面テキスト全消去；
   - `k`/`K`：入力待機（Wait Key）。テキストを消去せず次行に追記；
   - `r`：改行；
   - `B`/`E`（7バイト）：背景変更（地点ID + トランジションID）；
   - `C`（4バイト）：立ち絵表示（スロット`l/c/r` + キャラID）；
   - `D`：立ち絵消去（`Da`で全消去）；
   - `S`（10バイト）：背景と立ち絵を同時にアトミック切り替え；
   - `A`/`a`：3人立ち絵配置；
   - `V`/`H`：全画面CGまたはH-CGのロード；
   - `M`：BGM制御群（`Mf`フェード、`Ms`停止、`Mn`予約、`Mw`待機、`M00-M25`即時再生）；
   - `P`：PCM効果音再生（`P01-P13`）；
   - `F`：全画面白フラッシュ；
   - `Q`：全画面震動；
   - `X`/`s`：文字描画の水平オフセットおよびタイプライター表示速度。

メッセージを構造化セグメントとしてパースする：
```swift
public struct MessageSegment {
    public let actions: [InlineAction] // 当該セグメントで実行する演出一覧
    public let lines: [[Int]]          // 描画すべき葉コード行
    public let pause: MessagePauseType // 待機形式：.waitKey, .pageBreak, .messageEnd
}
```

## 5. 描画パイプラインとピクセル精度の再現実装

### 5.1 全画面サウンドノベルタイポグラフィと改行規則

- 画面全体（640×400）がテキストバッファ；
- 描画原点：`(20, 18)`；
- グリッド：横25文字 × 縦13行；
- 文字間隔：横送り24px、行送り28px（字高24px + 行間4px）；
- **改行規則**：Windowsオリジナル版には**禁則処理は一切存在しない**。横文字数`cur_x > 24`に達した瞬間に無条件改行される。

### 5.2 パレット輝度減衰と3パス重ね刷りハードシャドウ描画

1. **パレット輝度減衰（Latitude Darkening）**：
   テキスト表示中、背景画像はAlpha合成ではなく、DACパレットの輝度を一律スケールして暗転させる：
   $$\text{latitude\_dark} = \frac{11}{16} = 0.6875$$
   背景が全体的に31.25%暗転する。
2. **3パス重ね刷り描画**：
   1bppのフォントマスクを用い、フレームバッファへ3回書き込む：
   - パス1：`(x + 1, y + 1)`に純黒を書き込む（影1）；
   - パス2：`(x + 2, y + 1)`に純黒を書き込む（右側の影を太くする）；
   - パス3：原位置`(x, y)`に純白または灰色を書き込む（文字本体）。
   アンチエイリアス処理を一切行わないことで、1996年の鮮明なドット感を保つ。

### 5.3 入力待ちカーソルの厳密な意味論と点滅位相リセット

- **カーソル形状**：
  - キー入力待ち（`k`/`K`）：葉コード102（**右向き黒三角 ▶**）；
  - 改ページ待ち（`p`）：葉コード103（**紙アイコン**）。
- **描画位置**：最終文字の直後のグリッド内に描画。
- **点滅位相のリセット**：
  カーソルは6フリップ点灯・6フリップ消灯（200ms周期）で点滅する。
  *対策*：待機状態に入った瞬間に基準時刻をラッチし（`entryFlip = flipCount`）、**待機の第1フレームは常に点灯状態から開始する**。

### 5.4 地点番号の畳み込み（bgmap）と天候パレット（palmap）

1. **地点番号の畳み込み（`bgmap`）**：
   56個の地点番号は35枚の`MAX_S*.LFG`に集約される（例：地点4/5は`MAX_S02`、41/42は`MAX_S15`）。地点0は**画面消去（純黒）**。
2. **天候パレット（`palmap`）**：
   同一の教室画像に対し、9種類の天候パレットを用いて**パレットのエントリ0..3のみを差し替える（エントリ4の純白は保持する）**ことで、昼と夕方を表現する。
3. **欠落した VIS21 の扱い**：
   `VIS21.LFG`はディスク上に存在しない。オリジナルのコード内で、21番が要求された場合は`VIS02`を読み込んで紫色パレットを強制適用するよう実装されている。

### 5.5 13種類の LVNS 伝統トランジションの幾何学再現と高DPI対応

`sizuku_effect[13]`に定義された13大トランジション（パレットフェード、矩形螺旋、斜めタイル、菱形収縮、ディザ、櫛歯ワイプなど）。

- **所要時間計算（56フレーム効果の場合）**：
  切り替え全体 = `LvnsClear`（56フリップで旧画面消去）+ `LvnsDisp`（56フリップで新画面描画）+ 描画後静止30フリップ = **142フリップ（約2.36秒）**。
  トランジション実行中は仮想マシンをブロッキングする。
- **高DPIディスプレイへの適応**：
  Retina等の高解像度環境では、論理640×400へ一度縮小してトランジションマスクを計算し、それを整数倍拡大して表示することでブロックの解像感を維持する。

### 5.6 渦巻きトランジション（GURUGURU）のアルゴリズム修正

`mglvns`の`#ifdef USE_MGL`ブランチにはループ終了判定のバグがあり、第26列（全40列中）で螺旋が途切れて右側1/3が上からの百葉箱状の塗りつぶしに化けていた。

**修正**：`#ifndef USE_MGL`（Windows版ブランチ）に厳密準拠し、40×25タイルのグリッド上で`(27, 12)`を中心に螺旋臂を完全に対称展開させる。

### 5.7 Opcode 0x01 の4つのサブタイプと正弦波背景歪曲

- 第1式：正弦波背景歪曲を開始、テキスト終了後に黒へ暗転；
- 第2式：歪曲を維持したままフェードイン；
- 第3式：ブロッキング題字アニメーション（`sizuku01` 38コマ / `sizuku02` 19コマ）；
- 第4式：通常メッセージ。

#### 正弦波歪曲の数学とパイプラインフェーズ
361個のサンプリングテーブル`sintable[361]`を使用（振幅 $\pm 160\text{px}$、総和は固有値 **-1**）。
**描画フェーズ**：歪曲は**背景画像を描画した後、立ち絵と文字を乗せる前**に適用する。行ごとに`vram[x] = bg[x + shift]`でピクセルをずらすことで、文字は真っ直ぐなまま背景のみが大きく波打つ。

### 5.8 全画面バックログ（LvnsHistory）と二重テキスト VRAM

- 突入時に状態をスナップショット保存し、離脱時に完全復帰する；
- 背景画像は維持したまま、テキストバッファを`current_tvram = 1`に切り替え、1ページ分を一括描画する；
- 14箇所の`if (!history_mode)`ガードにより、立ち絵や効果音処理をバイパスする；
- 画面右端の▲ / ▼記号は第25列のフォントセルであり、クリック判定は当該セルの属性を読み取る。

## 6. 音声システムと macOS 低レベル工学的トラブルシューティング

### 6.1 BGM 番号マッピング（bgmmap）と CD-DA オフセット

スクリプト内のBGM番号は実ファイル名と一致しないため、変換が必要である：
```c
int bgmmap(int script_no) {
    if (script_no == 14) return 2;  // 特例：トラック2（Jingle）へ
    if (script_no < 16)  return script_no + 2;
    return script_no + 1;
}
```
実ファイル名は`MUS(track - 2).OGG`となる。このマッピングを怠ると、30%以上のシーンで誤った曲が流れる。
公式サウンドトラックとの音響指紋照合により、OP曲は78.2秒の`MUS14.OGG`（`MUS16.OGG`はエンディング曲）であることを確定した。

### 6.2 CoreAudio モノラル11025Hz例外の握り潰しによるプロセスハング

効果音再生時にプロセスがエラー出力なしで停止する現象が発生した。

#### 原因
効果音ファイルは**11025Hz モノラル WAV**である。
macOSの`AVAudioEngine`は**48000Hz ステレオ**で動作している。
フォーマットが一致しないバッファを`AVAudioPlayerNode.scheduleBuffer`に投入すると、CoreAudio内部でObjective-Cの`NSException`が送出される。
CLI環境ではクラッシュログが出力されるが、**AppKitのGUIアプリではメインRunLoop最上位の`@catch`ブロックが例外を静かに握り潰してコールスタックを巻き戻す**ため、ログなしでインタプリタが消滅し、無言のハング状態に陥っていた。

#### 対策
`AudioController`内で自動フォーマット変換を実装した：
```swift
private func convertedBuffer(from inputBuffer: AVAudioPCMBuffer, to targetFormat: AVAudioFormat) -> AVAudioPCMBuffer {
    if inputBuffer.format == targetFormat { return inputBuffer }
    guard let converter = AVAudioConverter(from: inputBuffer.format, to: targetFormat) else { return inputBuffer }
    let capacity = AVAudioFrameCount(Double(inputBuffer.frameLength) * targetFormat.sampleRate / inputBuffer.format.sampleRate) + 1024
    guard let outputBuffer = AVAudioPCMBuffer(pcmFormat: targetFormat, frameCapacity: capacity) else { return inputBuffer }
    var error: NSError?
    converter.convert(to: outputBuffer, error: &error) { _, outStatus in
        outStatus.pointee = .haveData
        return inputBuffer
    }
    return outputBuffer
}
```

### 6.3 60Hz クロックと macOS App Nap によるスロットリング

エンジンの時間基準は`INTERVAL = 60`で定義された**1/60秒（1フリップ）**である。

#### App Nap による1/12倍速化
ウィンドウが非アクティブになった際、macOSの**App Nap**機能によってタイマーが**約1Hz**まで間引かれ、毎秒5フレーム（1/12倍速）まで著しく低下した。

#### 対策
ゲームループ稼働中は、OSに対して遅延アサーションを明示的に取得する：
```swift
self.activityToken = ProcessInfo.processInfo.beginActivity(
    options: [.userInitiated, .latencyCritical],
    reason: "60 Hz reference flip loop (Lvns INTERVAL)"
)
```

## 7. 実戦的バイナリフォレンジック：時計塔の隠し音楽室（音楽モード）

### 7.1 突破口：タイトルメニューの第5の不可視ポインタ

`mglvns`のソースコードで音楽室がコメントアウトされていたため、原版には非搭載であると誤解されていた。
Capstoneを用いて`Sizuku.exe`のタイトルポインタ配列（VA `0x430ebc`）を逆アセンブルした結果、可視項目4つに加え、**第5のポインタ**を発見した。
その指すデータ：
`73 30`（"s0"） `58 35 36 59 31 32 38`（"X56Y128"） `ff ff` `72 24`。
これは、絶対座標を持つ空文字列の隠しエントリであった。

### 7.2 座標単位の数学的証明とピクセルアライメント

Leafの座標定義規則：
- `Y`：ピクセル単位；
- `X`：**半角文字幅（8ピクセル）単位**。

ターゲット物理座標：
$$X = 56 \times 8 = 448\text{px}, \quad Y = 128\text{px}$$
タイトル背景`TITLE0.LFG`上にマッピングした結果、**校舎右棟の上段右端の窓ガラス**に寸分違わず合致した。

### 7.3 音楽室本体ルーチンと葉コード 0x24 終端の罠

逆アセンブルを追跡し、`0x408d40`にジュークボックス本体を確認：
- 背景画像：`VIS17.LFG`（オルゴール）；
- 24曲のタイトルと作曲者テーブル；
- **終端罠**：曲名文字列は`0x24`（ASCII `$`）で終端されているが、`0x24`は日本語の葉コードの第2バイトとしても正当に出現する（例：「叔父さん」の「叔」）。単純に`0x24`で文字列を切り出すと曲名が途中で切断されるため、デコーダは厳密に2バイト単位で進める必要がある。

## 8. スタッフロールのブロッキングスクリプト解析

`0x7d END_BGM`で起動するスタッフロールはブロッキング実行される：
1. 14枚のカードを順次処理：背景ロード $\to$ 文字表示6秒 $\to$ パレット暗転16フリップ $\to$ 新背景明転16フリップ $\to$ 背景のみ表示1秒 $\to$ 文字表示；
2. 全体の所要時間は固定である：
   $$16 + (13 \times 436) + 76 = 5760 \text{ フリップ} \approx 96 \text{ 秒}$$
3. **CLICK_JUMP 仕様**：クリック時は即座に飛ばすのではなく、`selectPending`を立ててカードの6秒終了を待ってから最終カードへ滑らかに遷移する。

## 付録 A：主要 Opcode およびインライン制御文字リファレンス

### 1. 外側イベント Opcode

| Opcode | バイト長 | 引数 | 動作内容 |
|---|---|---|---|
| `0x00` | 1B | なし | Block終了 |
| `0x01` | 3B | `sub, arg` | 複合トランジション（正弦波歪曲/黒フェード/題字/テキスト） |
| `0x04` | 3B | `scn, blk` | JUMP：指定Blockへ遷移 |
| `0x05` | 可変長 | `msg, cnt, ...` | SELECT：選択肢メニュー表示 |
| `0x07` | 1B | なし | 直前の選択肢アンカーマーク |
| `0x0a` | 2B | `loc_no` | 背景設定（`bgmap`変換） |
| `0x14` | 2B | `type` | 画面完全消去（画像および文字） |
| `0x16` | 2B | `hvs_no` | H-CG背景ロード |
| `0x22` | 3B | `chr, pos` | 立ち絵表示（スロット指定） |
| `0x24` | 3B | `chr, pos` | アップ立ち絵（中央`'c'`強制） |
| `0x28` | 1B | なし | マーク2 |
| `0x38` | 2B | `effect` | 画面更新（`LvnsDisp`）+ 予約BGM再生開始 |
| `0x3d` | 4B | `flag, val, off`| 条件分岐（`flag[id] == val`） |
| `0x3e` | 4B | `flag, val, off`| 条件分岐（`flag[id] != val`） |
| `0x47` | 3B | `flag, val` | フラグ代入 |
| `0x48` | 3B | `flag, delta` | フラグ加算 |
| `0x54` | 2B | `msg_idx` | メッセージセクションのメッセージを表示 |
| `0x6e` | 2B | `bgm_no` | BGMループ再生（`bgmmap`変換） |
| `0x7d` | 2B | `bgm_no` | スタッフロールスクリプト実行 |
| `0x7e` | 2B | `ed_no` | エンディング番号記録 |
| `0xff` | 1B | なし | 終端番兵 |

### 2. 内側インライン演出制御文字

| 文字 | 引数長 | 記述例 | 演出動作 |
|---|---|---|---|
| `$` | 0B | なし | メッセージ終了 |
| `p` | 0B | なし | 改ページ待機（紙アイコン表示、クリック後消去） |
| `k`/`K` | 0B | なし | キー待機（▶アイコン表示、クリック後次行追記） |
| `r` | 0B | なし | 改行 |
| `B`/`E` | 6B | `B070808` | 背景ロード（地点07、効果08） |
| `C` | 3B | `Cr51` | 立ち絵ロード（右スロットに51番） |
| `D` | 1B | `Da`, `Dl` | 立ち絵消去（`Da`で全消去） |
| `S` | 9B | `S...` | 背景・立ち絵同時変更 |
| `A`/`a` | 可変 | `A...` | 3人立ち絵配置 |
| `V` | 可変 | `V01...` | イベントCGロード |
| `H` | 可変 | `H01...` | H-CGロード |
| `M` | 可変 | `Mf`, `Mn01` | BGM制御（フェード/予約/切替） |
| `P` | 可変 | `P01-P13` | PCM効果音再生 |
| `F` | 0B | なし | 全画面白フラッシュ |
| `Q` | 0B | なし | 全画面震動 |
| `X` | 2B | `X08` | 行描画水平オフセット |
| `s` | 1B | `s02` | タイプライター文字表示速度 |

## 付録 B：設計的逸脱およびアクセシビリティ拡張仕様対照表

| 項目 | 1996年原版の仕様 | macOS版の仕様 (Ver.1.0) | 設計理由 |
|---|---|---|---|
| **セーブスロット数** | 手動しおり3枠 + 自動退避1枠 | 手動しおり6枠 + クイックセーブ1枠 | 大画面デスクトップでの実用性向上のため拡張 |
| **セーブデータ形式** | 232バイトバイナリ構造体 | 構造化JSONテキストファイル | 将来の拡張性、互換性、可読性を確保 |
| **音楽室の入口** | 完全不可視、フィードバックなし | マウスホバーで白枠表示、メニューバー直行 | イースターエッグ性を保ちつつ発見性を付与 |
| **音楽室の脱出** | マウス右クリックのみ | 右クリックおよび`ESC`キー（ガイド表示あり） | 現代的なキーボード操作感への適合 |
| **回想画面の操作** | 画面右端の▲ / ▼記号をクリック | 記号クリックに加え、ホイールおよびタッチパッド操作 | macOS標準ハードウェアの操作性を活用 |
| **早送りキーの仕様** | ウィンドウメニューのみ、Enter長押し無効 | メニュー項目（Tab/Z）、キーリピート遮断 | 誤操作を排し原版の動作を忠実に維持 |
| **エフェクト省略** | コマンドライン引数 `-n e` | メニューバー「表示 $\to$ 画面エフェクトを省く」 | 内蔵機能を標準UIとして露出 |
| **カーソル字形** | フォントに▼なし（プログラム描画） | 葉コード102（▶）と103（紙）を厳格に使い分け | 待機意味論の混同を解消し正しく表現 |
